# 关键路径浏览器冒烟预验（交用户终验前的最后一道门禁）

> 来源教训：一次开箱流程改动，单测、E2E、构建门禁全绿，结果登录绑定、向导流程、入口卡死全是用户亲手点出来的——门禁零覆盖。确立本纪律。

## 触发条件

凡涉及**认证 / 开箱 / 下单 / 支付**等关键路径的改动，合入并重建运行环境之后、交用户终验之前，必须跑本流程。

## 核心纪律

1. **门禁绿 ≠ 用户能用。** 自动化测试覆盖的是"写代码时想到的路径"，用户走的是"真实交互路径"（点错、后退、刷新、换设备）。
2. 用浏览器操作能力（浏览器子代理或手动）**完整走一遍关键路径主链路**，例如：登录 → 开箱向导 → 核心绑定操作 → 换凭据二次登录 → 落地主面板。
3. **每步带落地断言**：到达的 URL 不是重定向中转页 + 页面存在该步的特征元素。只报"没报错"不算通过。
4. **截图留档**，随交付报告一起给用户——用户要看到"你替他先走过一遍"的证据。

## 红线

- **预验不得代用户完成终态操作**（如代建管理员账号、代删真实数据），除非用户明确授权重置/造数。预验环境优先用隔离测试环境。
- 预验发现问题 → 不交用户，回到修复循环，修复后复跑整条链路（不是只复跑出问题的单步）。

## 目标定位

这道门禁的目标不是"保证没 bug"，而是把**"用户亲手才能发现的 bug"尽量前置拦截**——用户每一次亲手抓到 bug，都是对协作体系信任的一次消耗。
